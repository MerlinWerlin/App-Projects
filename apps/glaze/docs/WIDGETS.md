## How the theme reaches the widgets

```
app/theme/[id].tsx  "Use this style"
  -> widgetThemeFrom(theme)            src/core/widgetTheme.ts (pure, tested)
  -> widgets.setTheme(...)             src/native/widgets.ts (no-op in Expo Go / Android, never throws)
  -> GlazeWidgetBridge.setTheme(json)  modules/glaze-widget-bridge (Expo module, Swift)
       UserDefaults(suiteName: "group.com.jared797.glaze")["glaze.theme.v1"] = json
       WidgetCenter.shared.reloadAllTimelines()
  -> ThemeStore.load()                 targets/widget/ThemeStore.swift (tolerant decode)
```

Photo widget: `widgets.setPhoto(fileUri)` makes the bridge re-encode the image as JPEG (long edge
≤ 1200 px) into the App Group container as `widget-photo.jpg`; `widgets.clearPhoto()` removes it.
Widget Studio calls `setPhoto` before saving a photo design; a cleared photoRef displays the placeholder instead of reusing an old photo.

The App Group `group.com.jared797.glaze` is added to the app by `native-plugins/widgets.json` and to the
extension by `targets/widget/expo-target.config.js`.

## Link check (T146, fb-1025 A)

`setTheme` returns true even without the App Group entitlement (`UserDefaults(suiteName:)` is never
nil), so a phone could not tell whether the app and the widgets actually share data. Now:

- **Extension** (`ThemeStore.load()`, every timeline / snapshot / placeholder): writes
  `{"at": ISO time, "themeId": …, "source": "defaults" | "file" | "fallback"}` as a JSON string to
  App Group UserDefaults key `glaze.widget.lastRead.v1`. If the extension lacks the App Group, the
  write lands in its private defaults and the app never sees it.
- **Bridge** `linkStatus()` (read-only): `containerOk` (the app can open the App Group container),
  `themeStored` (`glaze.theme.v1` present), `lastRead` (the string above or `""`) and `storedTheme`.
- **Adapter** `widgets.linkStatus()` (`src/native/widgets.ts`): `{ available: false }` in Expo Go,
  on Android and without the module; `{ available: true, supported: false }` for a build whose
  bridge predates T146 (unknown). Never throws.
- **Verdict** `widgetLinkVerdict(status, expectedThemeId, now)` (`src/core/widgetLink.ts`, tested):
  `expoGo` / `unknown` (nothing shown) → `noAppGroup` (no container, or the widgets drew the
  fallback after the app stored a theme) → `notReadYet` (no widget read visible yet) → `stale`
  (last read before the latest apply's `updatedAt`) → `wrongTheme` → `ok`.
- **Widgets tab**: one footnote line under the theme chips, native iOS builds only, checked on
  focus and 3 s after each theme pick (`src/store/widgetLink.ts`).

Reading a retest: "Home Screen widgets linked" means the widgets drew the app's theme. "App Group
missing" means the entitlement or provisioning profile is wrong on the app or the extension
(check both in the build's Signing & Capabilities). "Add a Glaze widget…" that stays after a widget
is on the Home Screen also points at the extension's App Group. Not yet confirmed on a device.

## Theme JSON schema (v1)

Stored as a JSON string. Source of truth: `src/core/widgetTheme.ts`; mirrored by `WidgetTheme` in
`ThemeStore.swift`.

```ts
type WidgetTheme = {
  v: 1;
  themeId: string;
  name: string;
  bg: string[];            // 1–2 '#RRGGBB'; two = top-to-bottom gradient (palette.bg, palette.surface)
  surface: string;         // '#RRGGBB'
  accent: string;          // theme.widget.accent
  ink: string;             // text colour
  style: 'glass' | 'solid' | 'outline';
  font: 'display' | 'body';
  updatedAt: string;       // ISO-8601
};
```

`parseWidgetTheme` (TS) and `WidgetTheme.init(from:)` (Swift) are tolerant: invalid colours, unknown
style/font or missing fields fall back to the Glaze default theme (plum to coral, T125); an unknown `v` is rejected.
Bump `v` and the key (`glaze.theme.v2`) for any breaking change.

Fonts: Unbounded/Manrope aren't bundled in the extension yet, so `display` maps to the system
rounded face and `body` to the system default.

## Widget sets (v2, T58 — core only)

> Core + tests only (`src/core/widgetSets.ts`). No UI, bridge or Swift reads this yet (T59).

Every theme gets a matching set: 5 kinds (`clock`, `date`, `photo`, `quote` with a countdown in
the large size, `battery`) × 3 sizes (`small`, `medium`, `large`), generated by
`generateWidgetSet(theme)` from the theme's tokens: palette, `widget.style`/`font`/`accent`, icon
shape (corner radius: squircle 22, circle 30, rounded 16, square 6, blob 26 pt), glyph set and
colour, `art.displayFont` and the first motif. Output is deterministic.

Each `WidgetSpec` has a nominal canvas (small 170×170, medium 364×170, large 364×382 pt), a
background fill (solid or gradient + opacity; glass is 0.82), an optional border (outline style),
and `regions` with fractional frames (origin top-start, so they mirror in RTL): `text`, `glyph`,
`photo`, `band`, `scrim`, `meter`. Text regions carry a `source` (`time`, `date`, `weekday`,
`month`, `dayNumber`, `week`, `monthGrid`, `batteryLevel`, `countdown` are formatted natively in
the device locale; `text` is an i18n sample key from `widgets.sample.*`), font role, size, weight,
alignment, whether it is editable and its length limit.

**Contrast.** Every text colour meets WCAG AA 4.5:1 against everything it can sit on; glyphs and
meters meet 3:1 (meters also against their track). Gradients are sampled; translucent layers (glass
over the wallpaper, the caption scrim over a photo) are bounded by compositing over black and over
white. If no colour works the generator makes the layer more opaque, then softens the gradient,
then flattens it — a flat fill always has a readable black or white. `region.backdrop` and
`region.contrast` record what was checked.

**Edits** (`applyWidgetEdits(spec, edits)`, for the future Widget Studio): per-region text
(cleaned of control characters, clipped to the region's limit in characters, `''`/`null` resets
to the sample), `photoRef` (photo widgets; a bare App Group file name like `widget-photo.jpg`),
`countdownTo` (`YYYY-MM-DD`, quote/large), colour overrides `background` (1–2 colours), `accent`,
`text`. Invalid edits are dropped with an issue `{ field, code, messageKey: 'widgets.issue.<code>' }`;
a text colour that can't reach AA is nudged (same hue) or replaced, with `contrastAdjusted`. The
result always meets AA.

**Payload.** `serialiseWidgetSet(set, { translate, now })` → JSON for App Group key
`glaze.widgets.v2`:

```ts
{ v: 2,
  theme: WidgetTheme,   // the exact v1 block (same shape/key order as glaze.theme.v1)
  tokens: WidgetTokens, // what the set was generated from
  specs: WidgetSpec[],  // 15, kind-major; each carries its applied `edits`
  texts: { [specId]: { [regionId]: string } }, // display text in the app language at write time
  updatedAt: string }
```

Compatibility: `glaze.theme.v1` is unchanged and should keep being written, so the current
extension works as-is; a v2-aware extension reads `glaze.widgets.v2` and can fall back to
`theme`. `parseWidgetSetPayload` accepts v2 or a bare v1 theme (upgraded by generating its set),
rejects other versions, and rebuilds every spec from `tokens` + `edits`, so a tampered payload
can't produce unreadable colours.

**Copy.** Kind names (`widgets.kind.*`), size names (`widgets.size.*`), sample text
(`widgets.sample.*`, original) and issue messages (`widgets.issue.*`) live in
`src/i18n/ns/widgets` in all 11 locales (non-English machine-translated, awaiting review). The
core module holds keys only; the app resolves them (and passes `translate` when serialising) so
the extension can show the user's language.

Sizes: home (170×170, 364×170, 364×382), **StandBy** (small canvas; the system removes the
background and tints red at night, so StandBy specs are solved on black), **accessory** circular
72×72, rectangular 160×72, inline 257×26 (VERIFY on device). Accessory specs are
`rendering: 'monochrome'`: no background or colours, just `tint` levels (`primary` 1.0,

**AA.** Same rules as the theme set: text 4.5:1, glyph / meter / dots / dial ticks 3:1 (dots and

**Maths** (`calendarMaths.ts`, all take `now` and an optional fixed UTC offset — no clock reads):

or a bare v1 theme; old readers (`parseWidgetSetPayload`) ignore the block.

**Copy.** New keys (`widgets.kind.<kind>`, `widgets.size.<size>`, `widgets.sample.*`,
`widgets.action.*`, `widgets.unit.*`, `widgets.habit.*`, `widgets.mood.1–5`,

planned, not built: see "Weather widget (plan, owner decision)" below.

## Interactive habit widgets (T73)

> **Code-complete, not compiled and not tested on a device.** There is no Xcode in the build
> environment: the Swift was written against well-known WidgetKit / App Intents API (iOS 17
> `Button(intent:)`, `AppIntent.perform()`) and reviewed by reading only. Nothing here has been
> run on an iPhone. Spots to check are marked `VERIFY` in the sources.

**What the person sees (full iOS build, iOS 17+).** Four Home Screen widgets, small and medium:
Water with − / **+150 ml**, Sleep with − / **+1 h**, Steps with − / **+500** (one step block,
typed in by hand, never read from a health store) and Mood (small: face + down / up; medium: five
faces to pick). Each shows today's value, the goal (count trackers) and a progress bar in the
active theme. Values go back to 0 at local midnight. In the app, the Widget Studio preview of a
habit widget shows today's value read back from the widget and the note
`tabs.widgetsTab.studio.habitButtons`.

**Expo Go, Android, older builds.** The adapter returns `{ available: false }` and the app never
calls native code: previews show 0 and the existing "Preview only" note
(`tabs.widgetsTab.buttonsNote`). The in-app preview buttons never do anything anywhere.

**Data flow (one writer per key).**

```
Home Screen widget button
  -> StepHabitIntent / SetMoodIntent.perform()   targets/widget/HabitIntents.swift (widget process)
  -> HabitStore.record(...)                      targets/widget/HabitStore.swift
       appends {seq, kind, op, amount, at, off} to glaze.habitLog.v1 (App Group UserDefaults)
  -> WidgetCenter.reloadTimelines(ofKind:)       widget redraws: trackers + taps not yet applied
App opens / comes to the foreground (Widget Studio mounted)
  -> useWidgetHabits()                           src/store/widgetHabits.ts
  -> widgets.syncHabits()                        src/native/widgets.ts (no-op fallback)
  -> GlazeWidgetBridge.getHabits()               modules/glaze-widget-bridge (both raw strings)
  -> syncHabitStore(habits, log, now)            src/core/habitLog.ts (pure, tested)
  -> GlazeWidgetBridge.setHabits(json)           glaze.habits.v1 with `applied: {logId, seq}`
```

- `glaze.habits.v1` (app only): `{ v: 1, habits: HabitState[], applied?: { logId, seq } }`. Old
  readers (`parseHabits`) ignore `applied`.
- `glaze.habitLog.v1` (extension only): `{ v: 1, logId, seq, events: [{ seq, kind, op: 'add' |
  'set', amount, at: epoch ms, off: UTC offset minutes }] }`. `add` is ± one step (mood: ± one
  level), `set` picks a mood face. `logId` is a UUID the extension picks when it starts a log; a
  new id means the app applies the whole log again from the start.
- **Merge** (`mergeHabitLog`): pending events (seq above the mark) in order; a tap on the tracker's
  day or later goes through the normal rollover; a tap from an earlier day (app closed over
  midnight) goes straight into that day's history; anything outside the 400-day window is
  ignored. Then every tracker rolls over to now.
- **Widget display** (`habitTodayValue`, mirrored by `HabitStore.todayValue`): the app's value for
  today (or its history entry for today) plus today's pending taps.
- **Caps.** Values stay inside the tracker's range (water ≤ 10,000 ml, sleep ≤ 24 h, steps ≤
  200,000, mood 1–5); one event carries at most the tracker's max; the log keeps the newest 400
  events and drops what the app has applied and anything older than the history window on the next
  tap. If someone taps more than 400 times without opening the app, the oldest taps are lost.
- **Step size** for a tap: the intent's `by`, else the app's tracker `step`, else the default
  (150 ml, 1 h, 500 steps).

**Swift files.** `HabitStore.swift` (tolerant JSONSerialization decode, value rules, log append
under an `NSLock`), `HabitIntents.swift` (`StepHabitIntent` with `habit` + `direction`,
`SetMoodIntent` with `level`; both `isDiscoverable = false`, `@available(iOS 17.0, *)`),
`HabitWidget.swift` (provider: one entry, refresh after midnight; views; original line-drawn mood
faces), registered in `GlazeWidgetsBundle.swift`. The extension's deployment target is 17.0, so
the bundle needs no `#available` check; `AppIntents` was added to the target's frameworks.

**Daily goals (T86).** Widgets tab › the **Goal: …** chip under a water / sleep / steps card
opens *Daily goals* (`app/habit-goals.tsx`): a − / + stepper per tracker (water 250–6,000 ml in
250s, sleep 4–14 h in halves, steps 1,000–50,000 in 500s; also a VoiceOver adjustable) and
"Back to <default>". Rules and validation: `src/core/habitGoals.ts` (tested). Only changed goals
are stored, in AsyncStorage `glaze.habitGoals.v1`, so goals work in Expo Go and on Android too.
`src/store/widgetHabits.ts` passes them to `widgets.syncHabits(now, goals)`, which writes them
into each tracker's `goal` in `glaze.habits.v1` (`syncHabitStoreWithGoals`); the bridge's
`setHabits` reloads the habit widgets, and `HabitStore.goal` reads it. The Widgets tab cards and
the Studio preview show today's value (full build) and the goal in force.

**Localised widget strings (T86).** The extension has its own `Localizable.strings` per app
language in `targets/widget/<lang>.lproj` (same 11 as the app). Habit copy goes through
`HabitText` in `HabitStore.swift` (`String(localized:defaultValue:)`, positional `%1$@ %2$@`
formats); App Intent titles and the other widgets' gallery names stay English literals used as
keys. `src/core/widgetStrings.test.ts` checks every language has the same keys and arguments and
that every Swift key exists. VERIFY on a dev build: the gallery and widget text follow the phone
language, and apple-targets copies the `.lproj` folders into the extension.

**Logging by hand in the app (T89, app side only).** Under every habit card on the Widgets tab a
"Today: 650 ml" button (≥ 48 pt, haptic, label + hint from `tabs.widgetsTab.log.*`) logs one step:
water +150 ml, sleep +1 h, steps +500 (the tracker's own `step`), mood to the next face (unset → 1
→ … → 5 → 1). A count tracker at its maximum buzzes a warning and changes nothing. Pure rules in
`src/core/habitTap.ts` (tested); `logWidgetHabit` in `src/store/widgetHabits.ts` shows the new
value straight away and runs every native read / write one at a time.

- Full iOS build: `widgets.logHabit` reads both App Group keys, `logHabitTapInStore` folds in the
  widget taps like a sync, adds the in-app tap to the app's trackers and writes **only**
  `glaze.habits.v1` (with the same `applied` mark it applied up to). The extension's
  `glaze.habitLog.v1` is never written by the app, so one writer per key still holds; widget taps
  appended after the read have a higher seq and are applied on the next sync.
- Expo Go, Android, older builds: the same trackers live in AsyncStorage under
  `glaze.habits.local.v1` (`logHabitTapLocal` / `readLocalHabits`), so the cards and the Studio
  preview show what was logged by hand. Nothing is copied into the App Group from there.

**Not yet.** No Lock Screen accessory
habit widgets natively (the catalogue's accessory specs have no buttons anyway; T89's Swift half is
held, D79-1). The extension still doesn't read the catalogue specs (`glaze.widgets.v2`), so the
habit widgets don't pick up per-widget Studio edits (colours, name text). No in-app undo for a hand
tap yet (mood wraps round; count trackers only go up); a custom step size per tracker isn't
offered (goals only).

## Widget Studio (T59)

> **Not tested on a device.** The in-app previews run in Expo Go; the App Group write needs a full
> iOS build with the updated bridge and has not been run on an iPhone.

- **Theme detail** (`app/theme/[id].tsx`, "Matching widgets"): one in-app preview per widget kind
  (small size), drawn by `src/ui/WidgetPreview.tsx` from the generated `WidgetSpec` (views +
  react-native-svg, so Expo Go works). Tapping one opens the studio on that widget. Kinds come from
  the set (`studioKinds`), so new kinds appear without UI changes.
- **Studio** (`app/widget-studio.tsx`, params `theme`, `kind?`, `size?`): live preview pinned on
  top; widget type and size chips; background row (photo on photo widgets, colour, gradient,
  theme art); accent and text colour circles (theme colours first, then original presets); text
  fields per editable region (limits from the spec) and the countdown day on widgets that have
  one; font chips each drawn in its own face; a stepped text-size slider (70–130 %, 5 % steps,
  VoiceOver adjustable); one "Add widget" button. Issues from `applyWidgetEdits` show as
  `widgets.issue.*` messages. Plus themes open the Plus sheet on "Add widget".
- **Logic** (`src/core/widgetStudio.ts`, tested): per-widget drafts, draft → `WidgetEdits`, the
  font/size restyle (applied after the edits; colours and AA contrast are untouched; scaled text
  never drops below 9 pt or grows past its region), swatch presets, tolerant parse of saved drafts
  (`glaze.widgetStudio.v1` in AsyncStorage, `src/store/widgetStudio.ts`), and `studioPayload`.
- **Payload**: `studioPayload(set, state)` = `serialiseWidgetSet` of the set with every draft
  applied, plus `studio: { selected: specId, styles: { [specId]: { font, scalePct } } }` (the
  v2 parser rebuilds specs from edits, so font/size live here). Photo widgets reference
  `widget-photo.jpg`; the preview's local file URI is never written.
- **Add widget** (full iOS build): `widgets.setPhoto(uri)` when the widget uses a photo, then
  `widgets.setTheme(v1)` and `widgets.setWidgetSet(json)` → bridge `setWidgetSet` stores it under
  `glaze.widgets.v2` and reloads timelines. Expo Go / Android / an older build without
  `setWidgetSet`: `{ available: false }`, and the screen says the design is kept as a preview.
- **Not yet**: the extension (`targets/widget`) does not read `glaze.widgets.v2`; it still renders
  from `glaze.theme.v1` (+ the photo). A v2-aware `ThemeStore` and per-kind widgets (battery) are
  follow-ups. No multi-photo "album" background yet (the bridge holds one photo).

## Widget looks (T65)

> **In-app preview only.** The extension does not read `glaze.widgets.v2` yet, so on a device the
> widgets still use the theme style. Not tested on iOS 26.

A **look** sits on top of the theme style (`src/core/widgetLook.ts`, MARKET.md gap 8):
`theme` (unchanged), `clear` (a frosted white or smoked black pane the wallpaper shows through),
`tinted` (the pane in the theme accent, or the user's background colour), `glow` (an original
neon look: a dark base made from the accent, bright text and glyphs with a soft halo; offered
second on dark themes, see `studioLooks`). Picked per widget in the Widget Studio ("Look" chips,
theme-set widgets; catalogue kinds since T85, below).

**Contrast pairing.** Tokens now carry `wallpaper`: the colours the theme wallpaper can show
(`designedColours`, max 8). `wallpaperBackdrop` adds blends between every pair plus the same for
the softened Home Screen version (T62 pair), so the result holds on either. `pairGlassText` /
the widget generator try panes faintest first (clear 12 %…100 %, white and black at each step;
tinted 32 %…100 %) and keep the first where every text line reaches 4.5:1 against the pane over
every one of those colours. Large numerals (time, day number, battery level, countdown that are
still ≥ 24 pt, or ≥ 18.67 pt bold, at the 70 % studio text size) need 3:1 under a look; words
always need 4.5:1. Glyphs and meters keep 3:1. Glow text is also checked against its own halo.
Without a known wallpaper (v1 theme, old payload) the pane is bounded over black and white, so it
just gets more opaque. `backdropFeasible` (exact gap test on luminances) skips panes no colour
could work on, and `compactByLuminance` trims samples without changing any verdict; the
relative-luminance helper is memoised.

**Payload.** Additive and backward compatible: `tokens.wallpaper`, and per spec `edits.look`,
`look`, `glow: { colour, opacity, radius } | null`. A clear/tinted spec keeps `surface: 'glass'`
(glow: `'solid'`), so an older reader still draws something sensible. Payloads without these
fields parse as the theme look; an unknown look is dropped (`notSupported`); junk wallpaper
colours are filtered. `glaze.theme.v1` is unchanged. Studio drafts store `look` (old drafts read
as `theme`).

**Native follow-up (VERIFY).** A widget can't see the wallpaper itself. On iOS 26 the system
draws its own glass in the clear/tinted Home Screen appearances (`widgetRenderingMode`
`accented`), so the extension should: draw `background` at `backgroundOpacity` in full-colour
mode, let the system glass replace it in accented mode (text then uses the system tint), and
draw `glow` as a shadow of `glow.colour`. Only the theme wallpaper's colours are checked; a user
photo as wallpaper is unknown to Glaze (until T85, below).

### Looks for every catalogue kind, wallpaper photo palette (T85)

**Catalogue looks.** All ten catalogue kinds (`widgetKinds.ts`) take the looks too, solved in
`build` the same way as the theme set (pane candidates first, glow tokens, halo samples,
`textMinContrast`). Which looks a size takes: `catalogueLooksFor(family)`: home sizes all four,
StandBy `theme` / `glow` (it is already on black and has no background to make glass of), Lock
Screen accessory sizes `theme` only (system-tinted). A look a size can't take is `notSupported`
and the spec stays `theme`. Catalogue specs and their `edits` carry `look` and `glow` like
`WidgetSpec`; a pane spec has `surface: 'glass'`. Widget Studio shows the Look chips for catalogue
widgets (draft `look`), and the Widgets tab has a look row that redraws every preview
(`setSpecInLook` / `catalogueSpecInLook`). Tests: every theme × kind × size × look keeps text at
≥ 4.5:1 (3:1 only for large numerals, never below 3:1) and graphics at ≥ 3:1.

**Your photo as wallpaper.** When a theme's background is the user's own photo (`usesPhoto`), the
app draws it (crop + theme tint) off screen at 36 × 78 px, reads the pixels through
`src/native/wallpaperPixels.ts` (react-native-view-shot PNG + the pure-TS `png.ts` decoder, so it
works in Expo Go) and `wallpaperPalette.ts` turns them into `tokens.wallpaper`: the k-means palette
(`paletteFromPixels`, k = 6) plus the per-channel darkest and lightest colours. A pane composite is
monotonic per channel, so every sampled pixel seen through the pane lies between the pane over
those two bounds, and the blends between them leave no luminance gap for text to hide in: text that
passes on the backdrop passes on every sampled pixel (tested against real wallpaper art). If
sampling fails or hasn't finished, the wallpaper is treated as unknown (panes bounded over black and
white), never as the theme design. The payload's `tokens.wallpaper` then holds the photo colours.
Limits: details smaller than the 36 × 78 sample average out; the Home Screen crop isn't modelled
separately.

## Weather widget (plan, owner decision)

> **Plan only (T75). Nothing is built.** Any option that shows real weather needs an exception to
> the "no network calls" rule in `ops/CONVENTIONS.md` and a change to the privacy text in the app
> (Settings → About/privacy) and the store listing. Facts below were checked on 18 Oct 2026 against
> the sources listed at the end of this section; re-check before building.

**Why it is not simple.** Weather needs two things Glaze has never had: the person's location and a
weather source on the internet. Every widget in the catalogue today is drawn from data already on
the phone.

**Permission flow (iOS).**
1. The widget extension's `Info.plist` gets `NSWidgetWantsLocation = YES`; the app's `Info.plist`
   gets the When-In-Use purpose string (`NSLocationWhenInUseUsageDescription`). Apple recommends
   When In Use for widgets ("better privacy and battery life"). We never ask for Always.
2. The app asks for When-In-Use permission itself, only when the person opens the weather widget in
   the Widget Studio (never at launch). Suggested copy: "Glaze uses your approximate location to
   show the weather in your widget. It stays on your phone and is only sent to the weather service
   to get a forecast."
3. When the person adds the widget, iOS asks separately whether to extend the app's location
   permission to the widget. The widget checks `CLLocationManager.isAuthorizedForWidgetUpdates`.
4. Location reaches the widget only while it is "in use" (shortly after it was visible). If the
   widget is approved but gets no fresh location, it shows the last known place and a small
   "location not updated" state; if not approved, it shows a "Choose a city in Glaze" state.
5. Put the weather widget in its **own widget extension** so iOS only asks for location for that
   widget, not for clocks, calendars and habits (Apple's advice for apps with mixed widgets).
6. Always offer a **manual city** fallback (typed in the app, stored in the App Group): no location
   permission at all, which also covers people who decline.
7. Use reduced accuracy: request `kCLLocationAccuracyReduced` / round to 2 decimal places
   (about 1 km) before the location leaves the phone. Under App Store definitions anything below
   3 decimal places is "coarse" location.

**Permission flow (Android).** Glaze has no Android widgets yet. A home-screen widget that refreshes
by itself (WorkManager, alarms, PendingIntents from widgets) counts as **background** location on
Android 10+, which needs `ACCESS_BACKGROUND_LOCATION` and a Google Play policy review that only
passes when it is "essential to core functionality". So on Android: manual city only, or location
read while the app is open and saved for the widget.

**Freshness (WidgetKit budget).** A frequently seen widget gets roughly 40–70 reloads a day (about
every 15–60 minutes); rarely seen pages get fewer; entries closer than about 5 minutes are ignored.
WidgetKit also reloads location widgets after a significant location change. So the plan is: one
fetch returns the next hours of forecast, the widget writes a timeline of hourly entries from it,
and asks for a new timeline after about 3 hours (or on a significant location change, or when the
app is opened, which does not count against the budget). Show the "updated hh:mm" time on medium and
large sizes. It will never be minute-by-minute, and we should not promise "live" weather in copy.

**Attribution.**
- Apple WeatherKit: every place that shows the data must clearly show the Apple Weather mark
  (the Apple logo followed by "Weather") and include the legal link to Apple's other-data-sources page. Severe alerts (if we
  ever show them) must link to Apple's alert page, name the source agency in full and never edit the
  alert text. Modified/derived data must say it is from "Weather" and has been modified.
  Plan: the mark inside the widget (small text line), the legal link in the app's weather settings
  screen and About screen (a widget has one tap target on small size). **VERIFY** in App Review
  that mark-in-widget + link-in-app is accepted; developer-forum threads suggest it is common.
- Open-Meteo: data is CC BY 4.0, attribution is required even on paid plans (credit + say if the
  data was modified). Same placement: short credit in the widget or the app, full credit and licence
  link on the About screen.

## Seamless widget (T131, owner brief themes-1024)

A Home Screen widget whose background is the exact piece of the wallpaper under it, with
transparent hero art (a planet, a moon) on top, so the art seems to float on the wallpaper.

- **Maths** (`src/core/seamlessWidget.ts`, tested): a device table keyed by native screen pixels
  (11 rows, 750×1334 to 1320×2868; generic names such as "6.7-inch 2796") with the widget sizes,
  the two column x positions and the three row y positions in native px. These are the
  community-measured figures transparent-widget tools use, **not** an Apple API: verify on device;
  the nudge fine-tunes. The 2622 and 2868 rows are scaled from their neighbours (`estimated: true`).
  Slots: small = top/middle/bottom × left/right; medium = top/middle/bottom; large = top or bottom
  (bottom starts at the middle row). `lookupDevice` matches Dimensions points × PixelRatio (the
  5.4-inch screen reports the 5.8-inch points, so it needs the native pixel size), else the nearest
  row. `seamlessCrop` maps the wallpaper aspect-filled and centred on the screen
  (scale = max(sw/W, sh/H)) and returns the crop in **wallpaper** pixels, whole and clamped inside
  the image; the nudge (±40 pt, 1 or 5 pt steps) moves it by points × scale. `heroRect` fits the
  hero inside the widget with 6 % padding.
- **Preview** (Expo Go): `src/ui/SeamlessWidgetPreview.tsx` draws a mock Home Screen with the
  wallpaper and one widget box that holds the same wallpaper at the negative crop offset plus the
  hero, with rounded corners, so it visibly blends in. `src/ui/SeamlessWidgetControls.tsx`: size,
  slot, step, four 48 pt arrows and reset; all text comes in through a `strings` prop.
- **Native**: `widgets.setSeamless({ wallpaperUri, cropPx, heroUri, size })`
  (`src/native/widgets.ts`; `{ available: false }` in Expo Go, on Android and with an older
  bridge) → bridge `setSeamless(wallpaperUri, x, y, w, h, heroUri, family)`: loads the wallpaper
  upright, `CGImage.cropping(to:)`, draws the hero centred-fit on top with
  `UIGraphicsImageRenderer`, caps the long edge at 1200 px, writes `seamless-<family>.png` into the
  App Group and reloads kind `GlazeSeamless`. The extension's `SeamlessWidget.swift` (small, medium,
  large; `.contentMarginsDisabled()`) fills `containerBackground` with that file, or shows the theme
  background and "Set up in Glaze" when it is missing.
- **iOS caveats** (say so in the setup copy):
  - The wallpaper must be set at the same crop: no Perspective Zoom, no pinch/move in the
    wallpaper editor, the same image file (the maths assumes aspect-fill, centred).
  - iOS may dim the Home Screen wallpaper (Dark appearance dimming, "Legibility" blur) or shift
    a wallpaper with depth effect; the widget does not dim with it, so the seam can show.
  - Tinted and clear Home Screen icon modes tint widgets too; the effect only holds in the default
    mode.
  - Lock Screen widgets are not supported (they cannot draw a full-colour image background).
  - ~~Each size keeps one image, so two widgets of the same size share it.~~ Since T221 each widget
    can pick its own piece (Edit Widget, below); the per-size image is the default.
  - The table is measured, not official: use the nudge until the edges disappear.
- **Not wired yet**: no screen uses the preview, controls or `setSeamless`; the lead connects them
  to the theme art packs (wallpaper 1290×2796 + transparent widget-small/medium/large.png). The
  widget's three strings have no Localizable.strings entries yet.

## 26 October native delivery audit (T155 / T79)

The editor previously wrote `glaze.widgets.v2`, but the extension did not read it. The new Foundation decoder reads the exact serialized editor payload, including the catalogue block, translated text, colours and per-size typography. An atomic `widgets.json` file takes precedence over cached UserDefaults. Theme writes now require an actual shared-container write; private UserDefaults alone cannot report success. A version handshake prevents an old binary from reporting edited designs applied. Saved drafts are retained before any delivery attempt.

Native widget types now include clock, date, photo, quote, analog clock, month calendar, countdown, month progress, year progress, water, sleep, steps and mood. Existing Lock Screen accessory and seamless widgets keep their identities. The five added types are registered in a nested bundle; existing installed widgets keep their kind identifiers. Month/year dots use the current calendar and refresh after midnight. Countdown uses the saved target date. Habit widgets retain their AppIntent actions and now consume saved background/accent/text colours.

Remaining limits: battery and photo-album designs, and habit accessory sizes, remain preview-only and are labelled before save. iOS controls accessory/tinted appearance; arbitrary Home Screen wallpaper blur is unavailable. System fonts stand in for the unbundled display font. The per-size shared design is common to all installed instances of that kind and size. A native build, not OTA alone, is needed. Compiler/decoder checks do not establish actual phone rendering or WidgetKit refresh timing.

Validation: `.github/workflows/glaze-widgets-check.yml` compiles the actual widget extension against the iOS simulator SDK and runs the Swift decoder against the real TypeScript editor payload. Run 40290905453 passed both. Existing colour/readability tests plus explicit gradient preservation across all bundled Home Screen designs pass. Full Windows suite has the same 19 failures on the base commit and repair; those unrelated SDK/source/path/asset guards are not hidden or claimed green.
