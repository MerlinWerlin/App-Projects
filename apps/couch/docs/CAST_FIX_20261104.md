# Photo/video casting repair — 4 November 2026

Jared reports that Couch connects to the TV but sending photos or videos fails. The TV remote connection and the media HTTP transfer use different channels.

Changes in this build:
- Real macOS HTTP testing reproduced a full-file GET timeout: incomplete Network.framework TCP messages stalled the sequential header/body sends. Each header/chunk write now completes its message; only the final chunk finishes the connection.
- The phone media server answers token-checked OPTIONS preflight requests and supplies an explicit reflected web origin, permitted Range headers, exposed content/range headers and private-network preflight permission. Both iOS and Android retain the existing random file tokens, range streaming and stop/revocation behaviour.
- Google Cast photo LOAD requests use a non-streaming photo and include the image URL in PhotoMediaMetadata. Video LOAD requests retain BUFFERED playback.
- The native HTTP regression job compiles the production Swift server on macOS (only Expo promise plumbing is stubbed), then checks actual preflight, full and ranged multi-chunk transfers, HEAD, invalid-token handling and revocation.

Google documents that Cast receivers use CORS for some media loads: https://developers.google.com/cast/docs/web_sender/advanced . Media message fields: https://developers.google.com/cast/docs/media/messages . These are concrete protocol gaps found in the source; they are not a confirmed diagnosis of Jared's particular TV without another device test.

This is a new iOS binary, version1.0.3, rather than an OTA-only update because the file server changed. The existing App-Projects release pipeline uploads it to TestFlight. Hardware confirmation remains pending: connect the TV, send one photo, send one H.264 MP4 video, seek the video, then stop. Check that the actual picture/video appears rather than relying only on a connected or sent status. Unsupported codecs, network isolation and TV-specific receiver behaviour remain distinct possible failures.
